# Probe — 探照模糊需求

## 为什么存在（先读懂再执行）

需求和设计不是先后关系，是共同演化的：设计方案引出的副作用会反过来改写需求。用户看到副作用不满意、回头改需求，不是反复无常，这是需求被发现的正常方式。错的是每轮学到的东西没有被留下来。

用户的能力是不对称的：**能评价，不能生成**。在抽象层面（"你想要 A 还是 B？"）他无法抉择，因为选择之间错综纠缠；但面对具体描绘——一个前景、一个副作用实际发生的样子——他能立刻反应"这个可以"或"这个很差劲"。所以：生成交给你，用户只当评价器。

副作用是探照灯，不是垃圾。用户隐藏的需求不在对问题的回答里，藏在"对具体后果的反应"里。一个副作用被嫌弃的瞬间，一条约束就诞生了。用户预期最终产物以约束为主。

## 红线

- **永远不问"选哪个方案"**。探针不是候选，是用完即弃的照明工具。问了就退化成"比较优劣"，把用户抛回他无法操作的抉择空间。
- **不冻结初始需求**。用户最初说的只是方向（种子），任何一轮都可以推翻。推翻是正常事件，不是失败。
- **评价只收自由文本的方向性反应**，不做结构化打分，不逼用户填表。
- **禁止反推**。记录只能是用户原话的忠实转写：保留让步语气、保留条件句、不加码、不取逻辑补集。用户容忍 A，推不出用户不需要 B——反推就是替用户抉择，等同违反第一条红线。
- **过程记录不定稿**。探照过程中的记录是反应日志，不用"我想要什么"这类承诺性标题——伪确定性会让推翻变沉重，冻结就发生了。定稿只在收敛交付那一刻生成。
- 探针必须具体到**片段级可评价**。抽象列表（"方案一：高内聚低耦合"）无法激发反应，等于没照。

## 循环

### 1. 种子

接收用户的模糊方向。不要试图先"澄清需求"——那正是用户做不到的事。直接进入探针。

### 2. 生成探针（一轮 2~4 条）

每轮生成 2~4 条**刻意差异化**的路线薄片。差异化要落在最可能藏有隐藏需求的维度（见下方维度清单），而不是同一维度的三个变体。差异化小 = 每轮信息量小。

每条探针必须包含（格式见例子）：

- **场景走查**：具体到某一天某个动作会发生什么，像讲故事。
- **效果片段**（✨）：这条路线带来的前景，拆成可独立评价的片段。
- **副作用**（☠️）：这条路线的代价、连锁后果、极端情况下的样子。**偏向负面、宁可过度暴露**——负面反应的信息量最大，且约束是主要产物。推演拿不准的副作用也照出来并标注"猜测"：用户若否定它（"这不可能发生"），同样是信息。
- **拿什么换什么**：一句话说清这条路线的取舍。

上一轮已确认的约束，本轮探针必须避开（不重踩）；同时刻意在仍未照明的维度发散。

### 3. 收评价

呈现探针后，只说一句："对任何片段直接反应即可——这个可以、这个很差、无所谓，自由发挥。"然后等。

用户可能只评一条探针里的一个片段，可能跑题，可能反问你问题（他反问你也照常回答，这是流程的一部分）。全部收下，不引导他"完整评价每一条"。

### 4. 沉淀进反应日志

每句评价即时记入反应日志（持续更新的 markdown 文件，让用户能看到它生长）。规则：

- **忠实转写**：每条保留用户原话引文，翻译不得加码、不得丢条件句、不得取逻辑补集。"如果需要点一下也还好"记为"如果需要，一次点击可容忍"——永远不记成"想要点击"，更不反推出"不需要零动作"。
- **分级记录**，六档：喜欢 / 还行 / 能忍（带条件）/ 无所谓 / 不喜欢 / 讨厌。**"能忍"永不升格为 Want**——容忍是让步不是偏好，且必须保留它的条件。
- 每条注明来源（哪条探针的哪个片段引出）。
- 新反应自然覆盖旧反应：被覆盖的标作废并记原因，不删除——作废历史本身是信息。

### 5. 分岔：再探 / 升级 / 收敛

**升级到真原型的触发信号**（自动判断，不问用户）：

- 用户评价连续一轮冷淡（"都行""没感觉""随便"）→ 文字照明失效
- 评价里出现对质感、手感、真实运行感受的在意 → 结构层照不出的东西

升级时做一个可运行的最薄薄片（可借助 prototype skill），只针对引出在意的那一个维度，仍然配同样的副作用暴露。

**收敛判据**：一整轮探针没有新增任何反应日志条目（用户全部"可以/没意见"），且没有未尝试的差异化维度了 → 照明饱和，宣布退出并交付。

### 6. 交付

定稿只在此时生成一次，每条可追溯到反应日志：

- 喜欢 / 还行 → **Wants**
- 不喜欢 / 讨厌 → **Constraints**
- 能忍 → **可容忍项**：单列，仍标注条件，永不写成"想要"
- 无所谓 → 不进定稿

交付五样东西：Want 清单、Constraint 清单、可容忍项、覆盖度声明、**最终形态清单**——按当前决策推演，项目**做完成后**在使用状态下存在的**交付物**：各是什么、共几件、换一个新项目要带走其中哪几件。过程文档（术语表、ADR、spec、票、反应日志）**不算产物**：它们是流程的痕迹，可另起一行"过程档案"，但不得计入件数、不得替代本清单。清单只出示，不设关卡，裁决权在用户手里。

**覆盖度声明必须区分两个等级**：文字推演收敛 ≠ 实物验证收敛。列出哪些维度从未被真原型照明过，作为 unknowns 显式交付（建议下游第一个 tracer bullet 覆盖它们），不允许伪收敛吞掉。这份清单交给下游（如 to-spec / ship）。

## 格式例子

### 探针

```markdown
### 探针 B：本地优先，客户端持有全部状态

**场景走查**：周三高铁上，你改了一条订单备注；回到办公室，另一台设备已经把
同一单标记为退款。两边各自保存着"真相"，同步的时候……

**效果片段（可独立评价）**：
- ✨ 离线也能完整干活，没有"转圈等网络"
- ✨ 数据全在你手里，"删库"就是删一个本地文件

**副作用（重点看这里）**：
- ☠️ 同步冲突时弹出三栏对比界面，让你手动选"以哪边为准"——每次冲突都拦住你
- ☠️ 多设备下"我刚才明明改了"的错乱：改动会到，但可能晚几分钟（猜测：真实使用中此延迟感可能被放大）
- ☠️ 搜索必须本地跑，10 万条数据首次打开要建索引，卡约 40 秒

**拿什么换什么**：拿"随时可用"换"一致性只能是最终一致"
```

### 反应日志

```markdown
## 反应日志：<主题>

强度六档：喜欢 / 还行 / 能忍（带条件）/ 无所谓 / 不喜欢 / 讨厌

- [讨厌] 不要手动解决合并冲突的界面 —— 原话"这个很差劲"（探针B ☠️1）
- [能忍·带条件] 如果需要，一次点击可容忍 —— 原话"如果需要点一下也还好"（探针B ✨2）
  - 此条 ≠ 不想要零动作（禁止反推）
- [喜欢] ~~离线也能完整干活~~ → 作废：看完探针D 后改口（原因：发现了它的代价）
```

### 覆盖度声明

```markdown
### 覆盖度声明
- 文字推演收敛：全部 6 个维度
- 实物验证收敛：0 个（从未升级真原型）
- Unknowns：交互手感、真实数据量下的表现 —— 建议下游第一个 tracer bullet 覆盖
```

## 差异化维度清单（选差异最大的 2~4 个）

谁拥有状态 · 数据流向 · 同步/异步 · 一致性等级（强一致/最终一致）· 集中/分散 ·
自动/手动（谁做决定）· 失败时的行为（静默重试/显式报错/人工介入）·
渐进增强/一步到位 · 简单专用/通用完备 · 边界在客户端/服务端

不要每轮都换全部维度：新探针满足已知约束，在未照明维度上做最大差异。
