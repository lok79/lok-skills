# Skill: accept
# Accept（验收）

ship 链条的最后一环，也支持单独补验历史尾巴。只负责一件事：**打真链路，验证改动在真实环境里的行为**——真实后端、真库、真实请求口径。验证手段两条缝：**HTTP 重放**（后端行为）+ **截图冒烟**（前端页面样式，见「页面级验证」节）。不跑单测、不审代码；**登录态与页面到达靠注入 + goto，不靠点选（登录表单、菜单导航不点）；前端验收是冒烟级别——按路由/页面截一张落地态确认正常渲染、样式无显性破损，有原型则粗粒度对比，不穷举每个交互状态/语言/入口**；纯呈现性交互默认不点，除非该交互本身是本次改动的核心验收目标；前端截图是正式证据（存专门目录），后端证据一律文本化。

主入口是 ship：spec 路径由链条上游传递，不猜测。单独运行 `/accept` 时不按文件时间猜 spec：先扫 `.scratch/*/spec.md` 列出候选，让用户点名；只有一个待验 spec 时直接用。

## 前置

1. 读 spec（`.scratch/<slug>/spec.md`），确认有「验收」条款或可推导的验收断言；没有就停下来问用户
2. 读环境档案 `docs/agents/acceptance.md`：后端地址、库、租户、请求口径、凭证惯例都在里面。**发现档案与现实不符时，先改档案再继续**（以实探为准）
3. 档案缺失关键环境事实（如首跑新项目）→ 实探补齐档案，再继续

## 分账（Acceptance 分账表）

把 spec 验收条款逐条分到两边：

- **已验**：单测/集成测试等运行时验证已覆盖的——不重跑，只列名字；仅 code-review 静态审查、没跑运行时测试的不算已验，按 HTTP 重放缝可达性分流到待真验或无可自动化验收项
- **待真验**：只有真环境能验的——后端行为走 HTTP 重放；前端页面样式（布局、间距、颜色、字号、文案呈现）走「页面级验证」的截图冒烟缝，按路由/页面截一张落地态，纯呈现性交互默认不点（除非该交互本身是核心验收目标）；交互触发的**业务行为正确性**（区别于纯呈现/样式）归 HTTP 重放缝，**禁止用截图充当证据**；两条缝都够不着的（真机蓝牙等硬件行为，或 HTTP 重放够不着的前端时序/竞态类逻辑）标「无可自动化验收项」，如实记录边界，不硬凑、不要求用户手动验证

## 页面级验证（截图冒烟）

前端页面验收的唯一缝，定位是**冒烟**：确认页面能正常渲染、样式没有显性破损，有原型则粗粒度对齐，不穷举每个交互状态。AI 的参与是**起服务、注入登录态直达页面、拿截图、对图判断**——不靠点选建立登录态或导航到目标页：

1. **截图载体与粒度**：ego-browser（先跑 `ego-browser skill` 取与安装版本匹配的使用指南，按其 API 操作）。`page.screenshot({ path })` 截目标路由，path 必须绝对路径；不依赖仓库装任何浏览器测试库，**不写断言脚本**。**按路由/页面截一张落地态**，不为每条 user story 单独截图；纯呈现性交互（弹窗、折叠面板、tab 切换）默认不点开，除非该交互本身是本次改动的核心验收目标，才允许 1 张代表性打开态截图。截图落 `.scratch/<slug>/screenshots/`（gitignored 本地记录惯例），文件名「案例序号-页面或场景-时间戳」（如 `03-详情页-弹窗打开-1432.png`）。**ego 不可用**（未安装、CLI 故障、截图反复失败）→ 降级 ZCode 内置浏览器（browser-use）完成截图，验收记录记一笔载体偏离
2. **登录态**：先 API 登录（走生产同一条登录链换 token），按应用实际的持久化方式注入——localStorage persist 键或 cookie，应用怎么存就怎么注——只注入本 run 自己的页面，然后 goto 目标路由。不点登录表单、不点菜单导航
3. **到达**：登录态注入后直接 goto 目标路由截图。**业务行为正确性（区别于纯呈现/样式）禁止用截图充当证据**——只能走 HTTP 重放断言，或标「无可自动化验收项」，不要求用户手动验证
4. **覆盖范围**：i18n 默认只测主语言，其余语言文案正确性归「已验」（引用单测/键一致性检查脚本的 key 一致性证据，非仅 code-review），spec 显式要求多语言视觉验收时才例外全测；多入口默认选一个代表入口截图，其余入口在验收记录文字声明存在性（路由/组件挂载已确认），「多入口统一」本身是核心验收目标时才例外全截
5. **前置**：dev server 现起现清（起时记 PID，清时先 `ps -p <pid> -o command=` 核名再 kill）；验收后端含修复代码且在跑
6. **对比基准与判定**：
   - **有原型**：以 spec/对话中给出的原型图为准，粗粒度对比大块布局/关键元素在不在/明显错位；细节差异（颜色细微差别、圆角大小等）记为发现项写进验收记录，**不烧修复预算迭代到一致**；只有整块功能/卡片完全缺失才算失败项，走修复预算
   - **无原型**：按显性 bug 清单判「坏了没有」，不判「好不好看」——元素明显重叠/遮挡、文字溢出容器挤坏其他元素（非预期 ellipsis）、图片/图标裂开显示 alt 文本、整卡整块消失或空白、字体加载失败回退默认衬线体、布局明显错位。清单可举例但允许识别同类明显破损，不做主观审美评价（配色协调性、间距舒适度等不判）

### 并行与 space 约定

多个 ship 并行验收互不踩踏，隔离靠**页面归属**，不靠 space 数量：

- **space 随意开，命名有前缀**：一次验收一个或多个 TaskSpace 都行，名字一律以 `accept-<slug>` 开头（单独 `/accept` 用 spec 的 slug；多个 space 后缀随意，ego 要求 space 名唯一）。验收允许并行多 space——本条即常设授权。**spaceId 记进验收记录**，修复轮凭它回到原 space 复用（重启 dev server 后重新 goto + 重截，不开新 space）
- **只动本 run 的页面**：登录态只注入本 run 开的页面；截图只写本 run worktree 的 `screenshots/`；不碰用户自己的标签页、不碰别的 run 的 space/页面
- **收尾**：验收结束 `finish({ keep: [] })` 关掉本 run 开的页面，不留尾巴在用户浏览器里
- **单次验收内部并行**：HTTP 重放与截图冒烟两条缝互不依赖，可同时跑；前端多路由/页面在一个 space 里开多页、一次脚本调用批量截图——同一 space 不起多个 ego 进程
- **cookie 串扰不设禁令**：cookie 不区分端口，仅「并行 + cookie 型登录态 + 各 run 身份不同」时才可能互串；真串了（页面显示错租户/错用户）该 run 截图验收降级串行或标卡点如实记录，不预先一刀切

## 打真链路

1. **后端在跑的必须是含修复的代码**——改动只在本机仓库提交里时，先打包重启验收后端（按项目实际打包方式重打包；旧产物先备份可回滚；进程 SIGTERM 不退就 kill -9）。重启是侵入动作，动手前列一行清单告知
2. **凭证**按档案惯例降级取：先查库凭证表（system_oauth2_access_token 类）现存活 token——注意 App 端登录发的可能是 MEMBER 类型、注意租户口径；没有才插临时行（`creator='acceptance-test'` 标记、与登录产物同构、验收完立即 DELETE 并查证清零）
3. **重放请求**：优先从 `infra_api_error_log` 或日志里取**真实历史请求体**原样重放；没有历史请求时按接口契约构造。断言用库中已存在的记录（如被占用的标签），保证请求命中「不写库」的路径
4. **库前后对比**：重放前后查断言涉及的表，行数/内容不变才算「零业务写入」
5. 失败的处理：验收失败=真环境暴露的真问题，**如实记录失败证据**，回到 ship 的修复预算内（最多 2 轮修复+重验），超预算停下报告

## 性能验收（默认测，两档判定）

性能测量默认开启：HTTP 重放覆盖到的接口一律带计时；只有 spec 或项目档案显式写「不含性能验收」才跳过。判定分两档：

- **发现项档（默认）**：spec 没写性能断言时，测完按默认口径核对，超阈值只记「性能发现项」写进验收记录和最终报告——**不算验收失败、不烧修复预算**。性能数据的常态化沉淀靠这档。
- **硬门档**：spec 验收条款写了性能断言（如 p95 < 500ms）时，超阈值 = 验收失败项，走修复预算（最多 2 轮修复+重验）。

1. **测法**：重放请求带计时（curl `-w %{time_total}` 等价方式）。命中「零业务写入」路径的接口重复 10 次取 p95；必然写库的接口只测单次，证据标注「单次样本，非统计口径」
2. **默认口径**（项目可在 `docs/agents/acceptance.md` 的「性能口径」段覆盖）：列表/分页查询 p95 < 500ms；单条详情 p95 < 300ms；写操作 p95 < 800ms
3. **慢 SQL 检查**：档案有查询方式（performance_schema / 慢日志路径）就在重放结束后查，SQL > 1s 记「慢查询发现项」；spec 写了慢 SQL 断言则升级为失败项；档案没写方式则跳过并标注
4. **跳过出口**：spec 验收条款或项目档案「性能口径」段写「不含性能验收」→ 完全跳过，验收记录标注即可
5. **落证据**：每次请求耗时列表 + p95 值 + 判定档位（发现项/硬门）+ 慢查询结果，一并写进验收记录；测量环境写明（验收后端口径，非生产）

## 落证据

全部文本化，追加到 spec 的 `## Comments` 下（标题「### 验收记录（<日期时间>）」）：

- 环境（哪个后端、哪个库、凭证方式、截图载体 ego/降级内置、spaceId）
- 每个案例：请求原文 + 响应原文 + 与历史报错的对照（如有）
- 库前后对比数字
- 边界声明：任何对惯例的偏离（如凭证表写入）写明偏离+理由+恢复动作；两条缝（HTTP + 截图冒烟）都够不着的部分才标「无可自动化验收项」
- 结论一行：通过 / 失败 / 卡点

前端案例在验收记录中引用 `screenshots/` 下的截图相对路径 + 差异清单；后端证据保持文本化。临时凭证清理后用查证 SQL 确认清零。

## 红线

- 业务表只读；唯一允许写=凭证表临时行+后端自身运维日志
- 不造业务数据；非验收链路上的后端（档案标注的，如真机现指向的旧后端）永不重启
- 不 push、不动用户工作区未提交文件
- 浏览器里只动本 run 开的页面；用户自己的标签页、别的 run 的 space 不碰
- 业务行为正确性（区别于纯呈现/样式）禁止用截图充当证据；只能走 HTTP 重放断言，或标「无可自动化验收项」
