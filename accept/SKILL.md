# Skill: accept
# Accept（验收）

ship 链条的最后一环，也支持单独补验历史尾巴。只负责一件事：**打真链路，验证改动在真实环境里的行为**——真实后端、真库、真实请求口径。验证手段两条缝：**HTTP 重放**（后端行为）+ **截图对比**（前端页面样式，见「页面级验证」节）。不跑单测、不审代码；**严禁 AI 驱动可见浏览器逐步点选（登录页、菜单、弹窗都不点）**；前端截图是正式证据（存专门目录），后端证据一律文本化。

主入口是 ship：spec 路径由链条上游传递，不猜测。单独运行 `/accept` 时不按文件时间猜 spec：先扫 `.scratch/*/spec.md` 列出候选，让用户点名；只有一个待验 spec 时直接用。

## 前置

1. 读 spec（`.scratch/<slug>/spec.md`），确认有「验收」条款或可推导的验收断言；没有就停下来问用户
2. 读环境档案 `docs/agents/acceptance.md`：后端地址、库、租户、请求口径、凭证惯例都在里面。**发现档案与现实不符时，先改档案再继续**（以实探为准）
3. 档案缺失关键环境事实（如首跑新项目）→ 实探补齐档案，再继续

## 分账（Acceptance 分账表）

把 spec 验收条款逐条分到两边：

- **已验**：单测/code-review 已覆盖的——不重跑，只列名字
- **待真验**：只有真环境能验的——后端行为走 HTTP 重放；前端页面样式（布局、间距、颜色、字号、文案呈现）走「页面级验证」的截图对比缝；交互行为（点击后出现什么）与两条缝都够不着的（真机蓝牙等硬件行为）标「无可自动化验收项」——交互行为在验收记录里声明由用户手点兜底，不硬凑

## 页面级验证（截图对比）

前端页面验收的唯一缝。AI 的参与是**起服务、拿截图、对图判断**，不是逐步驱动浏览器：

1. **截图载体**：ZCode 内置浏览器（browser-use）goto 目标路由直接截图，不依赖仓库装任何浏览器测试库，**不写断言脚本**。截图落 `.scratch/<slug>/screenshots/`（gitignored 本地记录惯例），文件名「案例序号-页面或场景-时间戳」（如 `03-详情页-弹窗打开-1432.png`）
2. **登录态**：先 API 登录（走生产同一条登录链换 token），注入 localStorage 对应 persist 键后进页面——不点登录表单、不点菜单，直接 goto 目标路由后截图
3. **前置**：dev server 现起现清（起时记 PID，清时先 `ps -p <pid> -o command=` 核名再 kill）；验收后端含修复代码且在跑
4. **对比基准**：有原型时，以 spec/对话中给出的原型图为准，渲染截图 vs 原型逐项对比；无原型时，用改动前基线截图 vs 改动后截图做 before/after 对比，判据用 spec 里的预期样式描述
5. **判定**：AI 读图，按间距/颜色/字号/布局逐项列差异清单（文本写进验收记录），标准是**视觉一致**而非像素级；差异在修复预算内迭代到一致
6. **交互行为**：点击后出现什么不在自动验收范围——验收记录声明，用户手点兜底

## 打真链路

1. **后端在跑的必须是含修复的代码**——改动只在本机仓库提交里时，先打包重启验收后端（按项目实际打包方式重打包；旧产物先备份可回滚；进程 SIGTERM 不退就 kill -9）。重启是侵入动作，动手前列一行清单告知
2. **凭证**按档案惯例降级取：先查库凭证表（system_oauth2_access_token 类）现存活 token——注意 App 端登录发的可能是 MEMBER 类型、注意租户口径；没有才插临时行（`creator='acceptance-test'` 标记、与登录产物同构、验收完立即 DELETE 并查证清零）
3. **重放请求**：优先从 `infra_api_error_log` 或日志里取**真实历史请求体**原样重放；没有历史请求时按接口契约构造。断言用库中已存在的记录（如被占用的标签），保证请求命中「不写库」的路径
4. **库前后对比**：重放前后查断言涉及的表，行数/内容不变才算「零业务写入」
5. 失败的处理：验收失败=真环境暴露的真问题，**如实记录失败证据**，回到 ship 的修复预算内（最多 2 轮修复+重验），超预算停下报告

## 性能验收（默认测，两档判定）

性能测量默认开启：HTTP 重放覆盖到的接口一律带计时；只有 spec 或项目档案显式写「不含性能验收」才跳过。判定分两档：

- **发现项档（默认）**：spec 没写性能断言时，测完按默认口径核对，超阈值只记「性能发现项」写进验收记录和最终报告——**不算验收失败、不烧修复预算**。性能数据的常态化沉淀靠这档。
- **硬门档**：spec 验收条款写了性能断言（如 p95 < 500ms）时，超阈值 = 验收失败项，走修复预算（最多 2 轮修复+重验）。

1. **测法**：重放请求带计时（curl `-w %{time_total}` 等价方式）。命中「零业务写入」路径的接口重复 10 次取 p95；必然写库的接口只测单次，证据标注「单次样本，非统计口径」
2. **默认口径**（项目可在 `docs/agents/acceptance.md` 的「性能口径」段覆盖）：列表/分页查询 p95 < 500ms；单条详情 p95 < 300ms；写操作 p95 < 800ms
3. **慢 SQL 检查**：档案有查询方式（performance_schema / 慢日志路径）就在重放结束后查，SQL > 1s 记「慢查询发现项」；spec 写了慢 SQL 断言则升级为失败项；档案没写方式则跳过并标注
4. **跳过出口**：spec 验收条款或项目档案「性能口径」段写「不含性能验收」→ 完全跳过，验收记录标注即可
5. **落证据**：每次请求耗时列表 + p95 值 + 判定档位（发现项/硬门）+ 慢查询结果，一并写进验收记录；测量环境写明（验收后端口径，非生产）

## 落证据

全部文本化，追加到 spec 的 `## Comments` 下（标题「### 验收记录（<日期时间>）」）：

- 环境（哪个后端、哪个库、凭证方式）
- 每个案例：请求原文 + 响应原文 + 与历史报错的对照（如有）
- 库前后对比数字
- 边界声明：任何对惯例的偏离（如凭证表写入）写明偏离+理由+恢复动作；两条缝（HTTP + 截图对比）都够不着的部分才标「无可自动化验收项」
- 结论一行：通过 / 失败 / 卡点

前端案例在验收记录中引用 `screenshots/` 下的截图相对路径 + 差异清单；后端证据保持文本化。临时凭证清理后用查证 SQL 确认清零。

## 红线

- 业务表只读；唯一允许写=凭证表临时行+后端自身运维日志
- 不造业务数据；非验收链路上的后端（档案标注的，如真机现指向的旧后端）永不重启
- 不 push、不动用户工作区未提交文件
